# Step 04: Policy layer

Status: complete and uncommitted. Migration `0004` is applied to `resolveai`, and 303 tests pass (185 need no database).

## How a write happens now

```
agent ──propose(tool, args)──> PolicyEngine ──approve──> awaiting_confirmation ──(read back)──> customer
                                   │ reject / require_human ──> rejected (speakable reason)
customer says yes (a later turn) ──confirm──> confirmed ──execute──> write tool
                                                                    │ locks customer, then order
                                                                    │ PolicyEngine again, on locked data
                                                                    │ amount must equal the confirmed amount
                                                                    └─> executed (or rejected)
```

- **Single source of values:** every rule value lives in `backend/app/policy/policy.yaml`.
- **One rule implementation:** the same `PolicyEngine` runs at proposal (to give early, speakable feedback) and at execution (the binding check).
- **Write tools can't be called around the gate.** The dispatcher refuses any write unless the session holds a `confirmed` (or, for replay, `executed`) action whose tool, arguments and idempotency key match.
- **Every decision is logged and persisted.** Each one is logged as JSON (`app.policy.decisions`) and written to `policy_decisions` with the rule that produced it, the facts it looked at and the policy version. Decisions are written after the main transaction, so a refusal at execution survives the write's rollback.

## Changes made

### Policy (`backend/app/policy/`, new)
| File | Why |
|---|---|
| `policy.yaml` | The single source of policy values:<ul><li>return window;</li><li>refund caps per order and per customer, with the rolling window;</li><li>refund processing time;</li><li>reship value cap;</li><li>shipping fee and free-shipping threshold;</li><li>missing-delivery grace period;</li><li>the remedy matrix (which issues allow reship and/or refund);</li><li>`escalate_when` flags (human review if true, refusal if false);</li><li>verification attempts;</li><li>confirmation expiry (turns and seconds).</li></ul>Money is in whole rupees, as integers only. |

| `gate.py` | The agent-facing API: `propose`, `register_customer_turn`, `confirm`, `cancel`, `execute`. ## Trade-offs

- **The engine is pure and facts are loaded separately.** Boundary tests run on in-memory objects in milliseconds, and the same function is the binding check under the row locks. **Rejected:** rules that query the DB themselves, which would be harder to test and impossible to run twice on the same snapshot.
- **The engine runs twice, at proposal and at execution.** The proposal decision is for speed and for the read-back. Only the execution decision, made on locked data, authorizes the write. If they disagree (the window closed meanwhile, or the balance changed), execution wins and the action becomes `rejected`.
- **The confirmed amount is binding.** If the amount computed at execution differs from what the customer heard, the write is refused with `confirmation_stale`. The customer only ever agrees to a specific number.
- **Every write tool needs confirmation, including `create_ticket` and `escalate_to_human`.** That's what the brief says. For escalation it's natural ("Shall I connect you with a colleague?"), and it still works before verification. **Rejected:** exempting escalation, which would make one write path that skips the state machine.
- **No same-turn confirmation.** `confirm` needs a customer turn after the proposal, so the model can't propose and confirm on its own. **Rejected:** trusting the model to wait.
- **The state machine is in memory, per session.** This matches the brief's "in-memory session state initially". It's auditable anyway: decisions are in `policy_decisions` and executions in `tool_invocations`. A restart loses unconfirmed proposals, so the customer is asked again. **Rejected for now:** a `pending_actions` table.
- **`rejected` is added as a terminal state.** The spec listed `cancelled` and `expired`. A policy refusal (at proposal or execution) is neither, and keeping it separate makes audits clearer.
- **`escalate_when` flags choose between human review and refusal.** "Which cases must escalate" is then real configuration with a defined meaning when it's off, and each message changes to match.
- **Per-customer cap counts pending plus succeeded refunds, excluding cancellations.** Money back for goods never sent isn't a remedy, and counting it would block legitimate claims after a cancellation. The window includes its start (`requested_at >= now - 30 days`).
- **Rule IDs are YAML key paths where a value decides the outcome.** An auditor can go straight from a decision to the line of config. Structural rules (`order.status`, `item.fulfilment`) use descriptive IDs.
- **Policy docs carry machine-checked front matter.** "Must agree with the YAML" is enforced, including the prose. Generating the documents from the YAML was rejected: retrieval works better on natural, human-edited prose.
- **Money in YAML is whole rupees.** It's easier for humans to read, `StrictInt` makes floats impossible, and it's converted to paise once in `config.py`.

## Challenges

- **Deadlock between concurrent refunds.** The step-03 concurrency test (two keys at once) started failing with `DeadlockDetected` once writes locked the customer. Each transaction first inserts its `tool_invocations` row. Its foreign key to `customers` takes a `KEY SHARE` lock, which conflicts with the other transaction's `SELECT … FOR UPDATE` on that customer, so each waits on the other. Fixed with `FOR NO KEY UPDATE` on the customer and order locks: writers still serialize, and FK checks don't conflict. Confirmed with 5 consecutive runs. I first used a non-existent SQLAlchemy argument (`no_key=`); the correct one is `key_share=True`, and I verified the rendered SQL.
- **Duplicate keyword bugs in the engine.** Two rules passed `deadline`/`eta` both explicitly and inside `**facts`. I caught this on review before any test ran.
- **Checking the boundary tests actually test boundaries.** All 54 engine tests passed first time, so I mutated each boundary comparison (`>` to `>=`) in a scratch copy. All 5 mutations were caught.
- **A test that couldn't reach the layer it targeted.** After the gate was added, a "reused key, different arguments" call is stopped by the confirmation check before it reaches the ledger. The test now asserts both layers: same session gives `action_not_confirmed`; a different session holding a confirmed action with that key gives `idempotency_key_reused`.
- **A hidden duplicate source of truth.** The refund timeline ("5 to 7 business days") was a constant in the tool, but it's customer-facing policy. It moved into the YAML so the docs check could cover it.
- **Unreadable config error.** The missing-remedies message showed enum reprs; it now shows the YAML keys.
- **Proved the docs check catches drift:** changing "30 days" to "14 days" in prose, or a cap in front matter, fails the test.
